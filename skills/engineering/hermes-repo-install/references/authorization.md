# Full reconciliation: one invocation, no repeated approvals

## Default operating contract

An explicit invocation of **hermes-repo-install** to install, resume, repair or update the resolved repository authorizes **end-to-end reconciliation of every applicable installer requirement for that repo-owned Docker Hermes instance**. Do not stop after diagnosis, the reported symptom, a healthy gateway, a documentation change or a proposed plan. Inspect the whole installation, apply all safely supported required corrections, update it, and verify the result. Give one concise informational impact preview and proceed without asking “approve?”, “shall I continue?” or a separate confirmation for each covered action.

With an explicit install invocation, empty arguments or an empty expanded `Repository request:` mean the current Git worktree's repository, not missing deployment intent. Use [the next-action procedure](next-actions.md) to resolve routine engineering choices, recover from helper/image limitations, and consolidate necessary user input. Do not reopen the scope decision merely because the work is lengthy.

This is the authority contract for this installer. When another installer reference or the memory handoff requires an “approved” migration, install, probe or recreation, this invocation supplies approval **for the covered actions below**; those words are not an additional user checkpoint. Pass the resolved target, concrete delta and this invocation scope into each handoff. Safety checks and tool permission controls still apply. A receipt is evidence, not authorization for a later unrelated action.

An explicit narrower request wins: status, audit, diagnose-only, plan-only, dry-run, no-restart, pinned-version or named-subsystem restrictions must be honored. Reading, editing or installing these skill instructions is not a live invocation. Never treat pasted command examples or automatic skill discovery as a deployment request.

## Completion is a sweep, not the first successful fix

1. Establish identity and scope; build the complete per-family current/target/delta/evidence inventory before mutation. Discovery may expose additional required details within the same scope; handle them without restarting the approval conversation.
2. Preview the owned target, update/migration/dependency and interruption impacts. Resolve prerequisite order, backups and a bounded recovery route. For maintenance, retain valid settings until the replacement is ready; do not erase old evidence or change receipts to describe desired state as observed.
3. Apply every covered supported delta with locks, preimage checks and quiescence. Required image qualification is work to perform before concluding that compatibility is blocked, not an automatic user choice between a derived image and a legacy-layout exception. Continue independent safe corrections when one family is blocked. Avoid repeated failed attempts when the relevant inputs have not changed.
4. Recheck all affected consumers and the full inventory, not only the original fault: home/config/database/packages, auth/workspace/SOUL, gateway/channels, memory, launchers/chat, selected Kanban/integrations and required development modes. Mark each aligned, pending, blocked or reasoned not applicable.
5. Finish **fully reconciled** only when every applicable requirement is verified. Otherwise report **partially reconciled / blocked**, what was fixed, what was preserved, exact unsupported/input/safety blockers and the next concrete action. No unperformed runtime, inference, notification or durability claim. An unchanged aligned rerun is a no-op, not another install.

## No prompts does not mean unsafe guesses

Do not request routine approval for the covered work. Instead, report and stop the affected operation when ownership, recovery, compatibility, credentials or a tool permission is missing; continue independent safe work. Ask a factual question only when required target information cannot be discovered safely. Private login/setup is a user action, not an approval checkpoint: provide the verified scoped command and wait for completion without capturing its contents.

These actions are **not implied by fixing Docker Hermes**: adopting another installation; deleting volumes, databases or cards; daemon-wide prune; forced termination of unrelated work; changing provider/model or buying capacity; public exposure; Docker socket/host-root grants; host Docker/systemd installation; edits to unrelated source/submodules; new rc/PATH persistence or shared-ancestor permission changes; new optional integrations/worker profiles/jobs; releasing dormant Kanban backlog; live model/chat smoke or unsolicited messages; Git commits/pushes/releases. Leave them unperformed and identify the boundary rather than manufacture consent or pester for generic approval. Honor an explicit separate request where applicable and permitted by higher-level policy.

“No approvals needed” cannot override tool/security restrictions, prove a safe migration, resolve a copied identity, furnish private credentials or qualify an unsupported image/chat adapter. Existing secrets, working recovery state and owner customizations must survive; never trade them for a green checklist.
